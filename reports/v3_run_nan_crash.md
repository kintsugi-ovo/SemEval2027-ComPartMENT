## 2. 报错信息为什么是误导的（第一个必须修的缺陷）

日志最后的报错是「回归头没有梯度：回归头没接进计算头」——**这是假的**。

`prepare_for_training()` 里：

```python
model = build_fn()
res = probe_fit_tier(model, data, t)     # ← 探针**真的训练了 2 步**，把 model 的权重改脏了
run_preflight_checks(model, data, ...)    # ← 用的是**同一份已被写坏的 model**
```

探针那 2 步产生 NaN 梯度 ⇒（无 AMP ⇒ 没有 GradScaler 兜底 ⇒ NaN 被写进权重）
⇒ preflight 拿到的模型权重已是 NaN ⇒ 纯 Huber 前向也是 NaN ⇒ 断言「头没接上」。

⇒ **真正的错误（梯度是 NaN）被完全掩盖**，排查方向被误导到「模型/计算图接错了」。

**已修**：探针之后**重建一个干净模型**再做 preflight。

## 3. 根因：组内 std 的灾难性抵消 + CUDA 原子累加的随机性

### 3.1 机制

v3.1 的 `L_guard` / `L_xrank` 依赖组内 std，而 std 由**矩**还原：

```python
var = (s2/n − mean²) · n/(n−1)      # s2 = Σx²，mean = s1/n
std = sqrt(var)
```

这是**灾难性抵消**：两个量级都是 `E[x²] ≈ 7~14` 的大数相减，结果却只有 `0.003~0.09`。
而预测值被 `5×sigmoid` 压在 [0,5] 且初始几乎一致 ⇒ **预测侧的 var 尤其小** ⇒ 抵消最严重。

### 3.2 实测（`scripts/diagnose_std_gradient.py`）

| 场景 | fp32 下的 var 相对误差 | fp64 下 |
|---|---|---|
| 预测 std ≈ 0.117 | **1.56%**（sqrt 导数被放大 64×） | 4.6e−13 |
| 预测 std ≈ 0.054 | **1.60%** | — |
| 预测 std ≈ 0.001（组内几乎相同） | **−148.8%（连符号都反了：算出 −4.8e−7，真值 +9.8e−7）** | 4.2e−09 |

### 3.3 为什么只有云端炸

1. **CUDA 的 `index_add_` 是原子加、顺序随机** ⇒ 同一个组的 var 在不同 batch 里**时正时负、时大时小**
   ⇒ `sqrt` 的导数在 0 附近剧烈跳动 ⇒ 梯度出现 `inf`/`NaN`；
2. **CPU/MPS 的累加顺序固定** ⇒ 抵消误差不会随机翻转 ⇒ 本地冒烟永远全绿；
3. **t3 档没有 AMP ⇒ 没有 GradScaler**（它本来负责跳过 `inf` 梯度的步）⇒ 坏梯度被**直接写进权重**。

### 3.4 为什么第一次运行就撞上

`en-nn` 有 **1 个目标只带 1 条例句**（实测：de-nn/en-pv/de-pv 的最小值都是 5，只有 en-nn 是 1）：

| 子集 | 目标数 | 每目标例句 min | 中位 |
|---|---|---|---|
| en-nn | 444 | **1** | 8 |
| de-nn | 461 | 5 | 6 |
| en-pv | 158 | 5 | 10 |
| de-pv | 158 | 5 | 10 |

探针用的正是 **en-nn**（RUN_PLAN 的第一次运行）⇒ 必然踩到。

## 4. 本阶段改了七处（全部在 notebook 真源里改，再同步到两个基线 notebook）

| # | 改动 | 文件 | 作用 |
|---|---|---|---|
| 1 | **组统计矩改用 float64 累加**（`stats_dtype_for(device)` 按设备能力选） | notebook 损失格 | 根因级修复：抵消误差 1.6% → 2.5e−9 |
| 2 | `std_from_moments` 加三道安全网：eps（sqrt 导数有界）+ `cnt≥2` 掩码（std 未定义的组整体退出）+ `nan_to_num` 兜底 | notebook 损失格 | 任何情况下都不产生 inf/NaN 梯度 |
| 3 | `xrank_parts` 只比较「组内例句数 ≥ 2」的目标 | notebook 损失格 | 避免「只有 1 条的目标」被当成「离散度最小」制造虚假大小关系 |
| 4 | **探针之后重建干净模型** | notebook 训练格 | 消除「权重被污染 ⇒ 报错指向错误方向」 |
| 5 | **探针阶段检查 `grad_norm` 是否有限** | notebook 训练格 | 数值问题在**探针**阶段就报错，且明确说明「不能靠降档解决」 |
| 6 | **preflight 改为走真实 `compute_loss` 反向 + 逐参数检查梯度有限** | notebook 训练格 | 原来只用 Huber 做反向 ⇒ **完全没覆盖 v3.1 的四个新分项** ⇒ 这就是 NaN 能溜过去的原因 |
| 7 | **训练期每 50 步验一次 loss 有限性**（`LOSS_FINITE_CHECK_EVERY`） | notebook 配置/损失格 | NaN 不再「静默训三小时」，第 50 步就停 |

### 附带修好的一个「反向陷阱」

第 1 项一开始写死 `float64` ⇒ **本地 MPS 直接崩**（`Cannot convert a MPS Tensor to float64`）——
而云端 CUDA 是支持 float64 的 ⇒ 这本身又是一个「本地与云端能力不同」的坑。
⇒ 改为 `stats_dtype_for(device)` 探测：CUDA/CPU → float64，MPS → float32（仍保留第 2 项的三道安全网）。

## 6. 下一次云端跑之前必须知道的三件事

1. **档位是 t3（Adafactor · 无 AMP · gradient_checkpointing）**：
   比上次的 t2（Adafactor · AMP）**慢 65%**（255 ms/样本 vs 155 ms），
   但 t2 按「两条基线中较大者 1550M」估算需 16.2 GiB > 13.1 GiB 预算 ⇒ 装不下 ⇒ 必须同档。
   投影：DeBERTa 约 3.3 h、Qwen 约 4.1 h（5 次运行 + 1.3 余量），在 12 h 上限内 ✓。
2. **t3 没有 GradScaler** ⇒ 坏梯度会直接写坏权重 ⇒ 本阶段加的三道防线
   （float64 累加 / 安全网 / 训练期有限性检查）是**必需品**，不是锦上添花。
3. **指标 2 的可测阈值是 0.153**，指标 1 是 0.065 ⇒ 云端结果必须按这两个阈值判读，
   小于阈值的变化**不能算收益**；且 nn 子集的指标 2 天花板只有 0.00–0.08，
   **不要把 nn 的指标 2 变化当成 v3.1 的成败**。
